# Adversarial review — M10 spec templating (`a392224`)

Branch `feat/templates`, one commit on `dfdbdcb`. Read-only review,
2026-09-08. Reviewed against the eight-item attack list.

## Verdict: REQUEST CHANGES (five P1, seven P2)

The module split is clean and the design intent is right: render before
parse, StrictUndefined, safe_load-only vars, one Jinja module. But the
wiring between `compile_pages` and `read_spec` does not implement the
contract the docstrings claim, and three of the four load-bearing
guarantees are false as shipped:

1. **`--set` is silently ignored by `compile-pages`** unless the page
   happens to carry its own `vars:` key on line 1 (P1-1). The refusal an
   operator gets says "pass it with `--set`" — for a variable they just
   passed with `--set`.
2. **`compile-pages` renders every spec even with no `--vars`/`--set`**
   (P1-2). Contract 1 is broken on the multi-page path. The goldens
   cited as proof never touch `read_spec`, so they cannot see it.
3. **Rendering is HTML-autoescaped** (P1-3). `from_string` lands on
   `select_autoescape`'s `default_for_string=True`, so every value
   containing `&`, `<`, `>`, `"` or `'` is silently mangled — a site URL
   with a query string, a title with an apostrophe.
4. **A malformed vars file echoes its own content** — the values — into
   stderr and into the on-disk manifest (P1-4). The test named
   `test_invalid_yaml_in_vars_names_the_file_not_the_content` asserts
   only that the file is named; it never asserts the content is absent.
   The module docstring cites a test (`test_secret_values_never_reach_output`)
   that does not exist in the suite.
5. **The `vars:` detection only ever matches line 1** (P1-5): `re.match`
   is anchored at position 0, so the `(?m)` flag is inert. A `---`
   document marker or one leading comment silently disables a page's own
   vars file — and where the shared `--vars` defines the same name, the
   page gets the shared value with no diagnostic at all.

Three attack-list items pass cleanly: no double rendering, no new DSL
authority, no zombie duplication. Details under "What passed".

**Verification gap.** `python`, `python3 -c` and every form of running
the suite were refused in this headless session ("requires approval").
The 465-test / ruff-clean / mypy-clean claims are unverified by me.

## Findings

### P1-1. `--set` is silently dropped by `compile-pages` for any page without a line-1 `vars:` key

- `src/formwork/multipage.py:255` builds the shared map with the `--set`
  pairs **deliberately excluded**: `shared_vars = resolve_variables(tv.vars_path, None)`.
- `src/formwork/multipage.py:176` seeds each spec's variables from that
  map only: `variables = dict(shared_vars or {})`.
- `src/formwork/multipage.py:199-200` is the *only* place `set_map` is
  ever merged in — and it sits inside `if own is not None:`
  (`src/formwork/multipage.py:183`), i.e. the branch that runs only when
  the spec's first line is `vars: <file>`.
- Failure scenario: `pages/brief.yaml` contains `title: {{ env }} brief`
  and no `vars:` key. `formwork compile-pages pages/ discovery.json
  --set env=Training` renders with `variables == {}`, StrictUndefined
  fires, and the page fails with
  `template variable 'env' is not defined (pass it with --set or in the
  vars file)` (`src/formwork/spec_templates.py:86-89`). The operator did
  pass it with `--set`. `formwork compile` on the same spec works, so
  the two commands disagree on whether the flag exists.
- No test covers it: the only end-to-end CLI test is
  `tests/test_spec_templates.py:159-183`, and it drives `compile`, not
  `compile-pages`. The `read_spec` unit tests always pass a `set_map`
  *together with* a spec whose line 1 is `vars: own.yaml`
  (`tests/test_spec_templates.py:142-155`).
- Fix: fold `--set` into the shared layer and keep the page-file layer as
  the only special case —
  `src/formwork/multipage.py:255` → `shared_vars = resolve_variables(tv.vars_path, tv.set_pairs)`,
  and move the `for k, v in (set_map or {}).items()` re-apply at
  `:199-200` out of the `if own is not None:` block (it is only needed to
  re-assert precedence *after* `variables.update(own_values)`, so it can
  stay inside the block *as well*, but the shared seed must already
  carry it). Add a `compile-pages --set` CLI test.

### P1-2. `compile-pages` renders every spec even when no `--vars`/`--set` was given — contract 1 is broken on the multi-page path

- `src/formwork/multipage.py:255`: `resolve_variables(None, None)` returns
  `{}`, never `None` (`src/formwork/spec_templates.py:101-104`).
- `src/formwork/multipage.py:290-292` therefore always passes a non-None
  `shared_vars`, and `src/formwork/multipage.py:205`
  (`if shared_vars is not None or own is not None:`) is always true.
- The comment directly above it —
  `src/formwork/multipage.py:201-204`, "With none supplied, the file is
  data: a literal `{{ ... }}` in a spec with no --vars passes through
  untouched (no-vars-no-change contract)" — describes a code path the
  production caller can never reach. The only thing that reaches it is
  `tests/test_spec_templates.py:101` (`read_spec(p, None)`), a call shape
  the CLI does not produce.
- Failure scenario: a spec that compiled fine on `dfdbdcb` and contains
  Jinja-ish text in a text part — a `{{ handlebars }}` example, a
  `{% ... %}` Liquid snippet in documentation copy, a `{# ... #}`
  sequence — now either fails the page with a template error or is
  silently rewritten (Jinja comments are deleted, `\r\n` is normalised to
  `\n`). Under `formwork compile` the same file is untouched, because
  `src/formwork/cli.py:196` gates on a truthy variable map.
- The commit message's proof does not cover this: the goldens under
  `tests/fixtures/expected/` are generator output built from module
  constants (`tests/test_generator.py:70-79`, `:679-690`) and never pass
  through `read_spec`. "Goldens diff empty" is true and irrelevant here.
- Fix: pass `None` when no template flags were supplied —
  `src/formwork/multipage.py:252-255`, e.g.
  `shared_vars = resolve_variables(...) if (tv.vars_path or tv.set_pairs) else None`,
  and widen `_Run.shared_vars` to `dict[str, Any] | None`. Then pin it:
  a `compile-pages` test over a spec containing a literal `{{ x }}` and
  no flags, asserting the title still reads `{{ x }}`.

### P1-3. Spec rendering is HTML-autoescaped: `&`, `<`, `>`, `"`, `'` in any value are silently mangled

- `src/formwork/spec_templates.py:76` renders with
  `environment().from_string(source)`.
- `.venv/lib/python3.11/site-packages/jinja2/environment.py:1111`:
  `from_string` builds the template with name `None`.
- `src/formwork/templating.py:33` configures
  `select_autoescape(enabled_extensions=("html.j2",), default=False)` and
  does **not** pass `default_for_string`.
- `.venv/lib/python3.11/site-packages/jinja2/utils.py:584` —
  `default_for_string: bool = True`; `:624-626` — `if template_name is
  None: return default_for_string`.
- `.venv/lib/python3.11/site-packages/jinja2/nodes.py:76-83` —
  `EvalContext.__init__` resolves `environment.autoescape(template_name)`
  with the template's name, i.e. `None`.
- So autoescape is **ON** for every spec render. Failure scenario:
  `--set site=https://contoso.sharepoint.com/sites/x?a=1&b=2` bakes
  `...?a=1&amp;b=2` into the spec text and thence into the payload;
  `--set title="Team's Home"` produces `Team&#39;s Home` as the page
  title. Nothing in the suite catches it — the one render assertion,
  `tests/test_spec_templates.py:91-93`, uses `"[4, 8]"`, which has no
  escapable character.
- This is also the one-environment rule biting: the shared environment's
  autoescape policy was written for *filenames* (`templating.py:5-9`),
  and `from_string` falls outside that policy by construction.
- Fix: keep the one environment but make the string default explicit and
  correct — `src/formwork/templating.py:33` →
  `select_autoescape(enabled_extensions=("html.j2",), default_for_string=False, default=False)`.
  That is a no-op for the existing `.js.j2`/`.html.j2` templates (both are
  loaded by name, never from a string; `render_template` at
  `templating.py:46` uses `get_template`). Pin it with a render test over
  `{"v": "a & b <c> \"d\" 'e'"}` asserting the value survives verbatim.

### P1-4. A malformed vars file echoes its own contents — the values — into stderr and into the committed manifest

- `src/formwork/spec_templates.py:43` interpolates the YAML error into
  the refusal: `DslError(f"{file}: invalid YAML in vars file ({_first_line(exc)})")`.
- PyYAML's error string embeds the offending **source line**:
  `.venv/lib/python3.11/site-packages/yaml/error.py:37-43`
  (`Mark.__str__` appends `get_snippet()`), built from the buffer at
  `:14-35`, and `MarkedYAMLError.__str__` at `:58-74` includes
  `str(self.problem_mark)` and `str(self.context_mark)`.
- Failure scenario: `vars.yaml` holds
  `site_url: "https://tenant.sharepoint.com/sites/finance` (unterminated
  quote) and `token: s3cr3t` below it. `formwork compile-pages pages/
  discovery.json --vars vars.yaml` prints, via `src/formwork/cli.py:489`,
  an `error:` line containing the literal text
  `site_url: "https://tenant.sharepoint.com/sites/finance` with a caret.
  Contract 3 says messages may name variables and files, never values.
- Worse on the multi-page path: `DslError` is a `ValueError`
  (`src/formwork/dsl.py:111`), so a page-level `vars:` file failure is
  caught at `src/formwork/multipage.py:296-297` and written verbatim into
  `PageResult.error` → `formwork-pages.json`
  (`src/formwork/multipage.py:120`, `:269`). The vars file's content
  lands in a build artifact that gets committed and shared.
- The test that claims to hold this line holds nothing:
  `tests/test_spec_templates.py:54-57` is named
  `test_invalid_yaml_in_vars_names_the_file_not_the_content` and asserts
  only `match=r"vars\.yaml"`. Its fixture (`key: [unclosed`) has no
  secret in it, so even an added negative assertion would have passed
  vacuously. And `src/formwork/spec_templates.py:13-15` cites
  "``test_secret_values_never_reach_output``-style tests" — no test of
  that name exists (`grep` over `tests/` returns nothing); the closest,
  `tests/test_spec_templates.py:85-89`, renders a template that never
  references the secret variable, so it can only pass.
- Fix: drop the interpolation at `src/formwork/spec_templates.py:43` and
  report position without content — PyYAML exposes
  `exc.problem_mark.line`/`.column`, so
  `f"{file}: invalid YAML in vars file at line {mark.line + 1}, column {mark.column + 1}"`
  keeps the diagnostic and loses the payload. Rewrite the test to write a
  vars file whose *broken line contains `SECRET`* and assert
  `SECRET not in str(excinfo.value)`. Same treatment for the chained
  `__cause__` at `spec_templates.py:43` and `multipage.py:210` /
  `cli.py:203` — use `from None`, since the rendered text those carry
  contains substituted values and would print in full under any
  traceback.

### P1-5. The `vars:` key is only ever detected on line 1; `(?m)` is inert and the misfire is silent

- `src/formwork/multipage.py:181`:
  `own_match = re.match(r"(?m)^vars:[ \t]*(\S[^\n]*)\n", text)`.
  `re.match` attempts the match at position 0 only, so the `MULTILINE`
  flag can never take effect. The docstring at `:177-180` calls it "a
  leading-line regex on a top-level `vars: file` entry" — but the code
  demands the *first* line, not any leading-column line.
- Shapes and what each does today:
  - `vars:` on line 1 → works.
  - `---` document marker on line 1, `vars:` on line 2 → **not detected**.
  - any leading comment (`# Training pages`) → **not detected**.
  - `vars:` after the `page:` block, still at column 0 → **not detected**.
  - `vars:` nested under `page:` (indented) → correctly not detected; but
    `spec.pop("vars", None)` at `:217` is top-level only, so the nested
    key survives into the spec and is ignored by the DSL (which has no
    unknown-key check — `_refuse_unsupported_page_keys`,
    `src/formwork/dsl.py:387-395`, only refuses `theme`/`navigation`).
  - `vars: "own.yaml"` quoted → detected, quotes stripped at `:182`.
  - `vars: own.yaml  # dev` → detected, and the comment becomes part of
    the path → `FileNotFoundError` (see P2-1).
  - a `vars:` line inside a `|` block scalar, on line 1 → impossible; on
    any later line → not detected, which is the right outcome by accident.
- Failure scenario, the silent one: `pages/finance.yaml` starts with
  `---`, then `vars: finance.yaml`, and the run also passes
  `--vars shared.yaml` defining `env`. The page's own `env` never loads,
  the shared `env` is used, the page compiles green with the wrong value,
  and `spec.pop("vars", None)` at `:217` deletes the evidence before
  anything downstream could notice.
- Fix: either (a) scan for the key with a line-oriented search that is
  actually anchored per line —
  `re.search(r"^vars:[ \t]*(\S[^\n#]*?)[ \t]*(?:#.*)?$", text, re.MULTILINE)`
  — and refuse (not ignore) a `vars:` that appears more than once; or
  (b) drop the per-page `vars:` key entirely. Note the ledger
  (`.hermes/plans/2026-09-07_milestone-ledger-m6-m10.md:81-83`) scopes M10
  to "Multi-page specs may share a vars file" — the per-page key is
  beyond that scope and is the direct source of P1-1, P1-5 and P2-1.
  Option (b) removes three findings at once. If it stays, make the
  detection failure loud: after rendering, if the parsed spec still has a
  top-level `vars` key that was never consumed, refuse.

### P2-1. A missing or mistyped vars file crashes the whole run with a traceback, breaking per-page isolation

- `src/formwork/spec_templates.py:40` calls `open(file, ...)` with no
  guard. `FileNotFoundError`/`IsADirectoryError` are `OSError`, not
  `ValueError`, so `src/formwork/multipage.py:294-297` does not catch
  them and `src/formwork/cli.py:488` (`except (DslError, ValueError)`)
  does not either.
- Failure scenario A: a page's `vars: prod.yaml` where the file was
  renamed. One bad page aborts `compile-pages` with a Python traceback
  after some payloads are already on disk and before
  `formwork-pages.json` is written (`src/formwork/multipage.py:269`).
  That contradicts the documented per-page isolation
  (`src/formwork/multipage.py:20-23`) and the "one error line, not a
  traceback" rule (`src/formwork/cli.py:483-485`).
- Failure scenario B: `formwork compile spec.yaml discovery.json --vars
  typo.yaml` — traceback, not `error: ...`.
- Fix: wrap the read in `src/formwork/spec_templates.py:39-43`:
  `except OSError as exc: raise DslError(f"{file}: cannot read vars file ({exc.strerror})") from None`
  (`strerror` carries no file content). Add a test for both scenarios,
  asserting a `FAIL` row in the manifest for A rather than an exception.

### P2-2. A `--vars` file that resolves to an empty mapping silently disables rendering, baking `{{ }}` into the page

- `src/formwork/cli.py:193-197`: `if not variables: return _read_yaml(path)`.
  The gate is on the *resolved map being non-empty*, not on the flags
  being present. `load_vars` returns `{}` for an empty or all-comments
  file (`src/formwork/spec_templates.py:44-45`).
- Failure scenario: a stub `vars.yaml` containing only
  `# env: prod  (fill me in)`. `formwork compile page.yaml discovery.json
  --vars vars.yaml` writes a payload whose title is the literal string
  `{{ env }}`, published to SharePoint. Contract 2 says a missing
  variable is a refusal naming the variable; here it is a placeholder in
  a live page.
- Note this is the exact mirror of P1-2: the CLI under-renders, the
  multi-page path over-renders, for the same reason — the render decision
  keys off the map's contents instead of the operator's intent.
- Fix: gate on intent in `src/formwork/cli.py:193-197` —
  `if getattr(args, "vars", None) is None and not getattr(args, "set", None): return _read_yaml(path)`
  — then always render when either flag was given.

### P2-3. `compile` and `preview` ignore a page's own `vars:` key and leave it in the spec

- `src/formwork/cli.py:189-204` (`_read_spec_text`) has no equivalent of
  the `own`/`load_vars` block in `src/formwork/multipage.py:181-200`, and
  no `spec.pop("vars", None)` (`multipage.py:217`).
- Failure scenario: `formwork preview page.yaml` on a spec whose line 1
  is `vars: page-vars.yaml` — the vars are not loaded, `{{ env }}` is
  either left literal (no flags, per P2-2) or refused. The same file
  under `compile-pages` renders correctly. The stray `vars` key survives
  into `compile_page`, where nothing rejects it (`src/formwork/dsl.py:387-395`
  is an explicit deny-list, not an allow-list), so it is silently ignored
  rather than diagnosed.
- Fix: move the whole read-and-render path into one function that both
  entry points call — `read_spec` already is that function; have
  `_read_spec_text` delegate to `multipage.read_spec(Path(path),
  shared_vars, set_keys, set_map)` instead of reimplementing two thirds
  of it. That also removes the duplicated
  "template rendered to invalid YAML" branch
  (`cli.py:200-203` vs `multipage.py:207-210`).

### P2-4. Values are spliced as raw text: YAML structural injection is possible, and autoescape prevents none of it

- `src/formwork/spec_templates.py:77` (`template.render(**variables)`)
  substitutes values textually; the result is fed straight to
  `yaml.safe_load` (`multipage.py:208`, `cli.py:201`). There is no
  quoting affordance — no `| tojson`, no YAML-quoting filter, and the
  README documents none.
- Failure scenario: `--set title=$'Ops\nnavigation: x'` or a vars file
  value containing `": "`, a leading `#`, a leading tab, or a newline
  followed by `  - text: injected`. The value changes the spec's
  *structure*, not just a scalar: an extra part, an extra top-level key,
  or a parse failure reported only as "template rendered to invalid YAML"
  (`multipage.py:210`) with no line number.
- The blast radius is bounded — the rendered text still goes through the
  same `yaml.safe_load` + `compile_page`, so `navigation:` is still
  refused (`src/formwork/dsl.py:393-395`) and nothing gains authority a
  literal spec lacks (see "What passed"). The exposure is that vars
  values increasingly come from CI variable stores, not from a human.
- Note the interaction with P1-3: autoescape escapes `& < > " '` — none
  of which are YAML structural characters — while leaving newline, `:`,
  `#` and tab untouched. It corrupts legitimate values and stops no
  injection.
- Fix: after P1-3, add a documented `| yamlq` filter (a one-line
  `yaml.safe_dump(value, default_flow_style=True).strip()` registered on
  the environment) and recommend it in the README for any operator-
  supplied scalar; at minimum refuse `--set` values containing a newline
  in `parse_set_overrides` (`src/formwork/spec_templates.py:60-68`) —
  naming the key, never the value.

### P2-5. Nothing records which variables produced a payload — M8's provenance claim is now false

- `src/formwork/provenance.py:88-96`: a `PayloadStamp` is the discovery
  header plus `spec` (the file *name*) and `compiledAt`. `compile` stamps
  at `src/formwork/cli.py:216`, `compile-pages` at
  `src/formwork/multipage.py:304`.
- Failure scenario: `--set env=staging` and `--set env=prod` over the
  same `brief.yaml` and the same discovery document produce two payloads
  with byte-identical provenance stamps and different page content. The
  manifest (`multipage.py:134-139`) records no vars either. The M8
  promise that a payload says what it was compiled from
  (`src/formwork/provenance.py:24-31`) no longer holds, and the M9 review
  spent two findings on exactly this class ("honest pins, ledger truth").
- Fix: extend the stamp with a `vars` block — the vars file's basename
  and sha256 over its exact bytes (same treatment as `discoverySha256`),
  plus the sorted list of `--set` **key names**. Never the values; the
  hash is the integrity check, the key list is the audit trail. Add the
  same three fields to the manifest header.

### P2-6. The new tests do not pin the contract; two pin states production cannot reach

Answering the attack-list question directly — of the 17 new tests:

- **No CLI test for `compile-pages` with `--vars`/`--set` at all**, and
  none for `preview`. `tests/test_spec_templates.py:158-183` is the only
  end-to-end test and it exercises `compile`. This is why P1-1 and P1-2
  shipped green.
- `tests/test_spec_templates.py:142-155`
  (`test_a_set_value_survives_a_page_vars_file`) passes
  `set_keys=frozenset()` alongside `set_map={"env": "shared"}`. Production
  always builds `set_keys` as `frozenset(set_map)`
  (`src/formwork/multipage.py:264-265`), so this combination cannot
  occur: with a real caller, a page vars file naming `env` always hits
  the refusal at `:191-195` instead. The test pins an unreachable state.
- `tests/test_spec_templates.py:85-89`
  (`test_a_value_never_reaches_the_error_message`) renders
  `"title: {{ missing }}"` with `{"other": SECRET}` — the template never
  references `other`, so no code path could have emitted it. It cannot
  fail. The real leak is P1-4, which this test's framing implies is
  covered.
- `tests/test_spec_templates.py:54-57` — see P1-4; the name asserts more
  than the body.
- `tests/test_spec_templates.py:97-102` is the *only* pin on the
  no-vars-no-change contract, and it calls `read_spec(p, None)` — an
  argument the CLI never produces (P1-2).
- The module docstring at `tests/test_spec_templates.py:13-14` states the
  precedence backwards: "--set overrides --vars, which overrides a page's
  own vars file". The implementation does the opposite —
  `src/formwork/multipage.py:196` (`variables.update(own_values)`) puts
  the page file *above* shared `--vars`, which is what the brief and
  `multipage.py:168-171` say. Fix the docstring, not the code.
- `tests/test_spec_templates.py:3` also points at
  `formwork.templating` for the contract; the contract lives in
  `formwork.spec_templates`.
- Fix: add (a) `compile-pages --set` with a page that has no `vars:` key;
  (b) `compile-pages` with no flags over a spec containing a literal
  `{{ x }}`; (c) `preview --vars`; (d) a render test with
  `& < > " '` in a value; (e) a vars-file YAML error whose broken line
  contains `SECRET`, asserting `SECRET` is absent from the message and
  from `formwork-pages.json`; (f) a spec whose `vars:` key is on line 2
  after `---`.

## P3 notes

- **P3-1. Dead branch.** `src/formwork/multipage.py:184-185` —
  `if not isinstance(own, str)` can never be true; `own` comes from
  `own_match.group(1)` (`:182`), always a `str`. Delete it, or make it a
  real check by parsing the value.
- **P3-2. Path handling around the `vars:` value.**
  `src/formwork/multipage.py:182` does `.strip().strip("'\"")`, which
  strips only one leading/trailing quote-class character and keeps any
  trailing `# comment` (→ P2-1 crash). `:186` resolves the path with no
  containment check, so `vars: ../../../etc/hosts` is read; combined with
  P1-4 that is a file-content disclosure primitive into the manifest for
  any non-YAML target. Low priority while specs are operator-owned, but
  it is the reason P1-4 should be fixed at the message, not at the
  caller.
- **P3-3. Dead parameter pinned by a test.**
  `src/formwork/spec_templates.py:96-97` — `resolve_variables(base=...)`
  has no production caller (`grep` shows only
  `tests/test_spec_templates.py:74`). Either wire it (it is the natural
  home for the page-file layer, which would fix P1-1 structurally) or

## What passed

- **No double rendering.** `render_spec_text`
  (`src/formwork/spec_templates.py:76-77`) compiles and renders once;
  substituted values are output text, not re-parsed as template source.
  A vars value containing `{{ other }}` is emitted literally. This is the
  right choice — recursion would make a vars file able to reach any
  variable in scope — and it should stay, documented.
- **No new DSL authority.** Rendered text goes through the same
  `yaml.safe_load` → `compile_page` path as a literal spec
  (`src/formwork/multipage.py:208, 293`; `src/formwork/cli.py:201, 215`).
  A template emitting `navigation:` is still refused with its citation
  (`src/formwork/dsl.py:393-395`, `UNMEASURED_PAGE_KEYS`), `bind:` still
  goes through the bind-key check (`dsl.py:310-313`), and extra sections
  are ordinary sections. No compile-time guard is needed *for structure*;
  the exposure is value-level (P2-4), not structural.
- **One environment, no fork.** `src/formwork/spec_templates.py:28`
  imports `environment` from `formwork.templating`; no second
  `Environment(...)` exists (`grep -n "Environment(" src/` → only
  `templating.py:30`). The `undefined=StrictUndefined` setting is
  inherited as intended (`templating.py:32`). The *autoescape* setting is
  inherited too, which is P1-3 — a policy bug, not a duplication bug.
- **No zombie duplication.** `src/formwork/templating.py` is unchanged by
  this commit and holds no `render_spec`/`resolve_variables` copy; the
  vars layer exists only in `spec_templates.py`. The `cli.py` aliasing
  (`render_spec_text as render_spec`, `:36`) and the split import in
  `multipage.py:54-61` are cosmetic.
- **`safe_load` only.** `src/formwork/spec_templates.py:41` and the
  non-mapping refusal at `:46-50` are correct; a vars file cannot execute
  anything or introduce a non-mapping root.
- **`--set` parsing.** `src/formwork/spec_templates.py:62-67` uses
  `partition`, so a value containing `=` survives intact, and the refusal
  at `:64-66` names the key only.
- **The shadowing refusal is a real refusal**, not a non-crash assertion:
  `tests/test_spec_templates.py:134` asserts
  `pytest.raises(DslError, match="explicit --set")` against
  `src/formwork/multipage.py:191-195`. The logic is right; it is only
  unreachable for the common case because of P1-1, and its sibling test
  pins an impossible state (P2-6).
