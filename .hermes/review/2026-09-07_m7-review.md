## Verdict: REQUEST CHANGES

Three P1s, all on the measured-claim side. (1) The `publish-flow` result cell is not what the template produces from this very fixture: the leg stringifies the whole 15-key `afterPublish.page.fields` object, the cell is a hand-typed three-key summary containing a field (`CheckoutUserId`) that is not in `PAGE_FIELDS` at all, so the commit message's "result cells aligned to the exact findprobe verdict strings" is false on the day it was written and no test re-derives the six verdicts from the fixture to catch it. (2) Four of the six verdicts embed run-specific values (page ids 16–21, the random slug, the `UniqueId`, the tenant `AbsoluteUrl`), so the next `findprobe` run reports DIFFERS on `filename-slug`, `layout-article`, `promoted-state` and `publish-flow` by construction; the three `psOk` verdicts are also tautological with respect to their claims (they say "create returned 201", not "FileName was ignored" or "PromotedState read back 0"), so a reversal of any of those claims would still print "same". (3) The `promoted-state` row's causal claim, "promoting an existing page to news is NOT an item-MERGE effect", is not established by the bytes: the POST sample was `Article`, the MERGE sample was `Home`, so the fixture cannot separate "MERGE is ignored" from "a Home page cannot be promoted". Under apply's actual conditions (Home layout, then `setFields({PromotedState})`, `_prelude.js.j2:188`, `apply.js.j2:13`) the measured outcome is 0 either way, which means the lane measured that `gen apply --promoted-state 1` ("1 = news post", `cli.py:311`) and README's "Copied: … promoted state" (`README.md:326`) do not do what they say, and the PR flags this nowhere.

The multi-page DSL is sound for the class of failure it names, with one real isolation gap (P2-6) and a provenance header that nothing consumes (P2-7). The test-side fixes were fixture-side as claimed; the weakening is in `test_findings.py` and predates the fold (P2-8).

## Findings

### P1-1. `publish-flow`: the cell cannot equal the verdict, and no test would notice

- Template: `verdicts["page.page-state.publish-flow"] = psRead("publish-state", "afterPublish.page.fields")` (`findprobe.js.j2:276-278`); `psPath` walks to the node and returns `JSON.stringify(node)` (`:257-265`). The node is the whole `fields` object of the page-entity read: `Id, Title, FileName, Url, AbsoluteUrl, UniqueId, PageLayoutType, PromotedState, Description, BannerImageUrl, BannerThumbnailUrl, Version, VersionInfo, IsPageCheckedOutToCurrentUser, FirstPublished` (`_probe_pagestate.js.j2:14-16`; fixture `discovery.pagestate.json:5829-5851`).
- Derived verdict from this fixture: `{"Id":21,"Title":null,"FileName":"0muuqfxy.aspx","Url":"SitePages/0muuqfxy.aspx","AbsoluteUrl":"https://shauntestazure.sharepoint.com/sites/TestSampleTeam/SitePages/0muuqfxy.aspx","UniqueId":"09388cec-fbd0-433c-b506-549d7aad1420","PageLayoutType":"Home","PromotedState":0,…,"Version":"1.0","VersionInfo":{…},"IsPageCheckedOutToCurrentUser":false,"FirstPublished":"0001-01-01T08:00:00Z"}`.
- Cell: `{"Version": "1.0", "CheckoutUserId": null, "IsPageCheckedOutToCurrentUser": false}` (`FINDINGS.md:57`, mirrored in the golden `tests/fixtures/expected/findprobe.js:317-322`). Three keys, Python `json.dumps` spacing (`": "`) which `JSON.stringify` never emits, and `CheckoutUserId` is an `ITEM_FIELDS` name (`_probe_pagestate.js.j2:17-19`; fixture `:5862`) that no `page.fields` path can yield.
- The comparison is `reprobed === row.result` (`findprobe.js.j2:291-294`), so this row is DIFFERS on the very data it was folded from.
- Why the gates passed: nothing in the suite computes the page-state verdicts from the fixture. `test_the_property_rows_carry_the_measured_values` does exactly that for the six property rows (`tests/test_findings.py:173-191`); the page-state rows got no equivalent, and `test_every_evidence_pointer_resolves_to_a_fixture_key` only asserts `pageState` is truthy (`:137-147`).
- Fix: make the leg emit the three-field summary it wants (`Version` from `afterPublish.page.fields`, `CheckoutUserId` from `afterPublish.item.fields`, `IsPageCheckedOutToCurrentUser` from the page) in a fixed wording, e.g. `fresh 0.1 checked out; checkoutpage 200; publish 200 -> 1.0, checkout cleared`, computed from `fresh`/`checkout`/`publish`/`afterPublish`; then add a Python test that mirrors `psOk`/`psRead` over `discovery.pagestate.json` and asserts equality with every `page.page-state.*` cell. That test fails today on this row, which is the proof it is a test.

### P1-2. Four verdicts are unreproducible by construction; three are tautological

- `psOk` returns `"ok (page " + s.pageId + ")"` (`findprobe.js.j2:255-256`). Page ids are server-assigned and monotonic (16–21 this run, `discovery.pagestate.json:4978, 5219, 5318, 5417, 5516, 5674`; recycled items keep theirs). The next run creates ids ≥ 22, so `filename-slug` (`FINDINGS.md:53`), `layout-article` (`:55`) and `promoted-state` (`:56`) print DIFFERS every time, and `publish-flow` carries `Id`, `UniqueId`, the random slug and the tenant origin (P1-1). Only `description-banner` and `permission-inheritance` can ever say "same". A re-probe that always says DIFFERS trains the operator to ignore DIFFERS, which is the one signal the registry exists to produce.
- `psOk` is `s.ok`, which `pageStateSample` sets whenever `run()` did not throw (`_probe_pagestate.js.j2:135-141`). `mergeItem` and `pageAction` never throw (`:86-127`), so a MERGE that returns 500 still yields "ok (page N)". Consequences per row:
  - `filename-slug` claims the FileName is ignored. The verdict never compares `requested.create.FileName` (`:4982`) with `persisted.created.fields.FileName` (`:5004`). If SharePoint started honouring FileName, the verdict is unchanged.
  - `layout-article` claims Article persists. The verdict never reads `read.page.fields.PageLayoutType` (`:5360`).
  - `promoted-state` claims MERGE reads back 0. The verdict says `merge flip: ok`, which reads as the opposite of the claim, and never reads `afterMerge.page.fields.PromotedState` (`:5619`) or the item's (`:5640`). If the MERGE started working, the verdict is unchanged.
- Fix: verdicts must be functions of the measured fields, not of the create's success or the page id. E.g. `FileName ignored (explicit); ignored (normalised)`, `PageLayoutType Article`, `create 1; merge 204 reads 0`, `null / persisted` (see P2-4), `false`. Nothing site- or run-specific belongs in a result cell; the M5 rows already follow that rule (`FINDINGS.md:36-52`).

### P1-3. `promoted-state`: the causal claim is confounded, and it falsifies a shipping path that the PR leaves untouched

- Claim (`FINDINGS.md:56`): "PromotedState 1 persists when sent at create (POST); the same field sent by item MERGE returns 204 but reads back 0 — promoting an existing page to news is NOT an item-MERGE effect".
- The two samples differ in two variables, not one. `promoted-at-create` is `{PageLayoutType: "Article", PromotedState: 1}` → 1 (`discovery.pagestate.json:5419-5422, 5434, 5461, 5482`). `promoted-merge-flip` is `{PageLayoutType: "Home"}` then MERGE `{PromotedState: 1}` → 204 (`:5604-5608`) → 0 on both entity and item (`:5619, 5640`). "MERGE does not honour PromotedState" and "a Home-layout page is normalised back to 0 regardless of write path" fit the bytes equally. The claim asserts the first. To establish it the lane needs a Home+POST sample and an Article+MERGE sample (`_probe_pagestate.js.j2:188-206`).
- On the brief's race question: no. The step order is create → read → `await mergeItem` (returns after the 204) → `readPageState` (`:201-206`); there is no delayed re-read, but the identical MERGE in `filename-explicit` (`BannerImageUrl`, `:5078-5082`) is visible in the immediate `afterMerge` read on both entity and item (`:5095, 5116-5122`), so the read path reflects a MERGE at once. The 0 is real; what is unproven is why.
- Consequence for the code: apply creates with `PageLayoutType: "Home"` (`_prelude.js.j2:186-189`) and then `created.setFields({ PromotedState: PROMOTED_STATE })`, an item MERGE (`apply.js.j2:13`, `_prelude.js.j2:197-218`). That is exactly the `promoted-merge-flip` conditions, which the template's own comment calls "the flip apply makes today" (`_probe_pagestate.js.j2:196-197`). Whatever the cause, the lane measured that `formwork gen apply --promoted-state 1` ("1 = news post", `cli.py:306-312`, pinned at `tests/test_generator.py:483`) and the copy path's "Copied: … promoted state" (`README.md:326`) leave `PromotedState` at 0. Neither the CLI help, the README, the CHANGELOG nor a comment on `apply.js.j2:13` says so. The registry's stated purpose is "the measured SharePoint claims formwork relies on" (`FINDINGS.md:3`); this row is the first one the code relies on the negation of.
- Fix: narrow the claim to what was measured ("on a fresh Home-layout draft, MERGE PromotedState 1 returns 204 and reads back 0; at create beside Article it persists"), add the two missing samples next run, and until then either warn in `gen apply` when `--promoted-state 1` is given or note in the help and README that the flag is measured ineffective on the create path apply uses.

### P2-4. `description-banner`: the verdict reads the pre-merge step, so "null / null" is not evidence for the claim

- Verdict: `psRead("filename-explicit", "read.page.fields.Description") + " / " + psRead(…, "read.page.fields.BannerImageUrl")` (`findprobe.js.j2:270-272`). `read` is the read **before** the MERGE (`_probe_pagestate.js.j2:161-163`): `:5037-5038` are null because nothing has been written yet. Any fresh page yields `null / null`; the verdict cannot move when the claim does.
- What `afterMerge` actually shows, and what the claim (`FINDINGS.md:54`) rests on: MERGE 204 (`:5078-5082`); page entity `Description: null` (`:5094`), `BannerImageUrl` = the requested URL (`:5095`), `BannerThumbnailUrl` derived (`:5096`); item `Description: null` (`:5115`), `BannerImageUrl` `{Url: …, Description: <the URL>}` (`:5116-5122`, note the empty `Description` sent came back as the URL, so the item value is not byte-exact to the request). The claim's two measured halves are supported by these lines. The cell is not an overclaim; it is a non-claim.
- The claim's third clause, "Description is a page-model field", is an inference: the lane never sent `Description` through `SavePageAsDraft` (`requested.pageModel` is `BannerImageUrl` only, `:4995-4997`). Measured is "item MERGE of Description: 204, stays null on entity and item". Say that.
- Fix: read `afterMerge.page.fields.Description` and compare `afterMerge.page.fields.BannerImageUrl` to `requested.merge.BannerImageUrl.Url` (a URL in a cell is tenant-specific; emit `persisted`/`not persisted`).

### P2-5. `filename-slug` overclaims "random slug"; the FileName-ignored result is Home-only

- Claim (`FINDINGS.md:53`): "A page created through sitepages/pages gets a server-assigned random slug (d0i8msje.aspx); the POST's FileName — explicit or slug-needing — is ignored".
- The fixture disagrees with the first half for two of its own six pages: the Article-layout creates got `Page.aspx` (`:5329`) and `Page(1).aspx` (`:5429`), a default name with a collision suffix, while every Home-layout create got an eight-character slug (`:5004, 5231, 5530, 5689`). The naming rule is layout-dependent, and the fixture shows it.
- FileName being ignored was measured on Home only (`:4982→5004`, `:5222→5231`). Whether Article honours it is unmeasured. The consequence "a spec cannot choose its page's file name at create" holds for apply's create path (Home), which is what matters for formwork, so keep the consequence and narrow the mechanism.

### P2-6. Multi-page isolation holds only for `DslError`/`ValueError`; a `TypeError` in one spec aborts every page and leaves payloads without a manifest

- `_compile_one` catches `yaml.YAMLError` and `ValueError` (`multipage.py:215-221`). `compile_page` raises other things on valid YAML: `column: [1]` → `int([1])` `TypeError` (`dsl.py:463`); `type: [one]` → `[…] not in SECTION_FACTORS` `TypeError: unhashable type` (`dsl.py:456`). `main` catches only `(DslError, ValueError)` (`cli.py:427`), so the operator gets a traceback, `compile_pages` never reaches the manifest write (`multipage.py:200-204`), and the payloads already written for earlier specs sit in `out_dir` with no `formwork-pages.json` describing them. The docstring promises "a spec that fails … fails alone" (`multipage.py:19-22`); the tests cover only the `DslError` and YAML classes (`tests/test_multipage.py:174-203`).
- Fix: catch `Exception` in `_compile_one` and record `f"{type(exc).__name__}: {exc}"` (the per-page row is exactly the place a traceback should become a line), and add a test with `column: [1]` in one spec asserting the other still builds and the manifest is written.

### P2-7. Provenance is recorded and never consumed: compile-against-A, apply-on-B is not caught

- The manifest header has `discoverySha256`, `discoveryWebId`, `discoveryWebUrl`, `discoveredAt` (`multipage.py:60-89, 136-141`). The payloads carry none of it (`:222-228`), `gen apply` takes a payload path only (`cli.py:256, 304`) and the apply script reads `.canvas` and `.title` (`apply.js.j2:8, 36-37`) on whatever site the paste-in runs from. Nothing reads `compiledWith`. The module admits stamping is deferred to M8 (`multipage.py:16-18`); the README says the manifest "carries the run's provenance header" (`README.md:202, 240`) and stops short of claiming enforcement, so this is a documented gap rather than a false claim. Answer to the brief's question: no, it would not catch it, and neither would a human reading the manifest, because apply records no target web id to compare against.
- Smaller: the hash is over `read_text()` output (`multipage.py:194`), which translates `\r\n` on Windows, so "hashed over its exact bytes" (`:80`) is true only where newline translation is a no-op. `read_bytes()` for the digest makes it true everywhere.
