## Verdict: REQUEST CHANGES

Two P1s. The first is the one that matters: `bind:` emits a list-binding shape that the M5 probe never sent and refuses the one it did. Every ListWebPart binding the probe stored carries `selectedListUrl` **server-relative** (`/sites/TestSampleTeam/Formwork Probe Docs`) next to `webRelativeListUrl` **web-relative** (`Formwork Probe Docs`) — `discovery.m5.json:4605-4607, 4649-4651, 4755-4757, 4799-4801` — but `part_bind` writes the same web-relative value into both keys (`dsl.py:263-264`) and refuses a leading slash (`dsl.py:257-262`). The docstrings, the constants' comments and the test pin all describe a measurement that is not in the fixture. The second P1 is that `preview` still lays out sections from `type` alone, so a `columns:` section previews as one 12-wide column and any part in column 2 is silently dropped from the picture. Everything else is P2/P3 and mostly small.

## 1. `properties:` on component parts

### Verified

- **Flat scalars reach `web_part_data.properties` over the manifest defaults.** `_control_for` builds `dict(component.default_properties) | _flat_scalars(...) | part_bind(...)` (`dsl.py:493-495`); `_flat_scalars` refuses dict, list and `None` values with the M5 citation (`dsl.py:180-187`) and a non-mapping `properties` (`dsl.py:178-179`). Pinned at `tests/test_dsl.py:703-711, 736-738`.
- **The 12/12 claim matches the fixture.** `webpartProperties.requested` has 12 rows (`discovery.m5.json`, ids `…-0005-000000000001` … `000000000012`) and `persisted` has 12 rows, every one `present: true` with `storedValue` equal to `newValue` (showChrome true/false, layoutId CompactCard/List, captionText ""/"Formwork caption probe: image", layout Filmstrip/Compact, heroLayoutThreshold "640"/"320", isDocumentLibrary false/true). `skipped` is `[]`.
- **bool-vs-int via `type(declared) is not type(sample.new_value)` is correct** (`dsl.py:205`). `type(True) is bool`, `type(1) is int`, so `showChrome: 1` refuses against the measured bool and `showChrome: true` compiles; `heroLayoutThreshold: 640` refuses because the probe measured that path as the **string** `"640"` (`discovery.m5.json`, ids `…-0005-000000000009/10`). The identity check is stricter than `isinstance` and that strictness is what the measurement supports. `declared is None` at `dsl.py:203` is unreachable after `_flat_scalars` and harmless.
- **The type check is keyed on the alias the fixture uses.** `cat.property_samples_for(component.alias)` (`dsl.py:201`, `catalogue.py:252-253`) against `sample.component` = `"NewsWebPart"` etc.; a part named by title resolves to the same `Component` (`dsl.py:408-420`), so the gate is not bypassable by spelling.
- **Unmeasured components are unconstrained**, as claimed (`dsl.py:201` loop is empty; `tests/test_dsl.py:757-761`).
- **No colon fold on web-part data**: attributes go through `escape_attribute` and the text fold lives only in `_text_control` (`dsl.py:540, 576`); `tests/test_dsl.py:724-734` pins it.

### Findings

- **P2** `_flat_scalars` is a deny-list, not a scalar allow-list, so any YAML scalar that is not JSON-serialisable passes it and crashes with a raw traceback. `dsl.py:181` excludes only `dict`, `list`, `None`; the value reaches `json.dumps` in `_escaped` (`dsl.py:583`, called at `dsl.py:499, 505`), which raises `TypeError` for `datetime.date`/`datetime.datetime`, `bytes` (`!!binary`), `set` (`!!set`). `main` catches only `(DslError, ValueError)` (`cli.py:290-294`); `TypeError` is neither, so the operator sees a traceback. This is reachable from an ordinary spec: PyYAML's SafeLoader resolves an unquoted `2026-09-07` to a `date`, and EventsWebPart's measured property block carries `startDate` / `endDate` (`discovery.m5.json`, ids `…-0005-000000000007/08`, `"startDate": ""`), so `properties: {startDate: 2026-09-07}` is exactly what an author would write. Fix: `isinstance(value, (str, int, float, bool))` — which is also what "flat scalar" means, and the measured sample types are exactly `bool` and `str`. A `float('nan')` from YAML `.nan` would additionally serialise as bare `NaN`, which is not JSON; the allow-list should reject non-finite floats too.
- **P2** A text part's `properties:` and `bind:` are silently ignored. `_part_kind` only requires exactly one of `component`/`text` (`dsl.py:401-405`); the text branch of `compile_page` (`dsl.py:616-623`) never reads either key and returns before `_flat_scalars`/`part_bind` run. `emphasis` on a text part is refused with a citation (`dsl.py:372-377`, pinned at `tests/test_dsl.py:374`); these two keys should get the same treatment, or "nothing is silently dropped" stops being true for the new keys.
- **P3** `_type_check_against_samples` consults `new_value` only (`dsl.py:201-205`). `PropertySample.value_round_tripped()` / `stored_present` (`catalogue.py:127-135`) — the half of the measurement that says whether the path *survived* — is never read by the DSL, so a path the probe measured as dropped or altered would still compile without a word. No live impact today (12/12 survived), but the gate uses half the evidence it cites.
- **P3 (pre-existing, not in this diff)** `displayTitle` is still unvalidated: a non-string flows into `web_part_data.title` verbatim (`dsl.py:489`) and into the part record (`dsl.py:645`). Listed because the attack brief named it; it predates M5.

## 2. `columns:` on sections

### Verified

- **Shape and sum.** 1–3 factors, each 1–12, summing to 12 (`dsl.py:278-290`); `type`+`columns` refuses (`dsl.py:272-276`); the type-only path returns `SECTION_FACTORS[type]` unchanged and tagged `"measured"` (`dsl.py:293-296`). Pinned at `tests/test_dsl.py:775-814`.
- **MEASURED_FACTOR_SETS membership is consistent with the fixture.** (8,4) and (4,8): `layoutVariants.persisted` has all four variants with `sectionFactor` 8 (sec 17), 4 (sec 18), 8 and 4 (sec 19) — `discovery.m5.json`, ids `…-0006-000000000001` … `04`, requested equals persisted control data. (12,), (6,6), (4,4,4): the M5 `storedCanvas` carries controls at sectionFactor 12 ×56, 6 ×24, 4 ×26, 8 ×2, which is the M2-era one/two/three placement sections plus the M5 variants, as the comment at `dsl.py:130-136` says. Any set in both paths is tagged `"measured"` by both (`dsl.py:291-292, 296`): consistent.
- **The warning text names the measured sets of the same width** (`dsl.py:319-321`), and `warnings.warn` with the default filter *does* reach stderr from the CLI (UserWarning is not in Python's default ignore list) — but see the two findings below on how often and where it points.
- **Nothing downstream reads `Placement.section_type`** except through `spec` in preview (grep: `dsl.py:110, 346` only), so the stale `"one"` it carries for a `columns:` section (`dsl.py:316, 346`) is wrong data with no consumer today.

### Findings

- **P1** `formwork preview` renders a `columns:` section with the `type` geometry and drops parts. `build_preview` validates through `placements(spec)` (`preview.py:64`), which accepts `columns:` — and then lays the section out from `SECTION_FACTORS[section.get("type", "one")]` (`preview.py:69-73`). For `columns: [8, 4]` that is one column of factor 12, `by_slot[(index, 2)]` is never read, and every part with `column: 2` vanishes from the HTML with no error. The preview's own contract is "a spec that previews has the geometry … a compile would emit" (`preview.py:3-5`). Fix: make `preview.py:68-74` call `section_factors(section, index)` (already public in `dsl.py:268`) instead of indexing `SECTION_FACTORS`, and add a preview test with a two-column `columns:` section that asserts both parts render. `cli.py:129-139` has no `--discovery`-independent path that avoids this.
- **P2** `section_factors` raises `KeyError`, not `DslError`, when `columns` is combined with an unknown or null `type`. The conflict message indexes `SECTION_FACTORS[type_name]` inside the f-string *before* the type has been validated (`dsl.py:272-276`), so `type: bogus, columns: [8, 4]` and `type: null, columns: [8, 4]` (`"type" in section` is true for a null) both traceback through `cli.py:290-294`. The unknown-type check at `dsl.py:293-295` is reached only when `columns` is absent. Fix: `SECTION_FACTORS.get(type_name)` in the message, or validate the type first.
- **P2** `test_unmeasured_but_legal_combo_warns_and_compiles` does not assert the warning fired. `tests/test_dsl.py:817` opens `warnings.catch_warnings(record=True)` without binding the record list, and the only assertion is `assert result.canvas` (`:825`). The comment "parts_out carries warnings" (`:823-824`) is false: `parts_out` records kind/component/title/emphasis/where/boundTo (`dsl.py:641-653`) and nothing about factors. Delete `warnings.warn` at `dsl.py:322` and this test still passes. Fix: `with pytest.warns(UserWarning, match=r"\[5, 7\].*unmeasured")`.
- **P3** The warning fires twice per unmeasured section through the CLI and points at formwork, not at the spec. `compile_page` calls `placements(spec)` twice (`dsl.py:591` for `wants_text`, `dsl.py:610` for the walk); with `stacklevel=2` (`dsl.py:326`) the two call sites are two distinct warning-registry locations, so Python's `default` action prints both: `…/dsl.py:591: UserWarning: section 1: …` and again for `:610`, each with the source line echoed. Operators are told refusals reach them "as one error line" (`cli.py:287-289`); the warning path does not get the same care. Fix: compute `placements(spec)` once in `compile_page`, and either route the warning through `_cmd_compile` as a `warning:` line or record it in the part output so the CLI can print it — which would also make the comment at `tests/test_dsl.py:823-824` true.
- **P3** `int(f)` at `dsl.py:283` coerces silently: `columns: [8.9, 4]` compiles as (8, 4) with no mention of the 8.9; `[true, 11]` is (1, 11); `["8", "4"]` is (8, 4). `catalogue.py:170` already has the right predicate (`isinstance(v, int) and not isinstance(v, bool)`); reuse it and refuse the rest.
- **P3** `dsl.py:328-330` is unreachable: `section_factors` has already raised for an unknown type without `columns` (`dsl.py:293-295`) and for `columns` with any `type` (`dsl.py:272-276`).

## 3. `bind:` on list-bound parts

### Verified

- **Key spelling matches the fixture.** `BIND_TARGET_KEYS` values `selectedListId`, `selectedListUrl`, `selectedViewId` and the literal `webRelativeListUrl` (`dsl.py:152-156, 264`) are the four keys every ListWebPart binding carries in both `requested` and `persisted` (`discovery.m5.json:4248-4252, 4605-4609` and the three siblings). The probe's own block agrees (`discover.js.j2:359-363`).
- **Unknown-key, missing-key and GUID-shape refusals** (`dsl.py:230-241, 247-253`); the properties∩bind collision refusal runs before any control is built (`dsl.py:626-636`), and `compile_page` is the only caller of `_control_for` (grep: `dsl.py:639`), so no shipping path builds a bound control without the collision check. `boundTo` is recorded from the spec's own values (`dsl.py:650-653`); pinned at `tests/test_dsl.py:918-933`.
- **`bind: {}` refuses** (not `None`, so `dsl.py:236-241` reports both missing keys); `bind: null` reads as absent (`dsl.py:225-227`).

### Findings

- **P1** `bind:` writes an unmeasured `selectedListUrl` and refuses the measured one. What the probe sent and SharePoint stored, for the library part and the list part against both targets: `selectedListUrl` = `/sites/TestSampleTeam/Formwork Probe Docs` (server-relative) beside `webRelativeListUrl` = `Formwork Probe Docs` (`discovery.m5.json:4605-4607` persisted, `:4248-4250` requested; list target `:4755-4757` / `:4431-4433`, and the two cross-bindings). The probe template documents exactly that: "selectedListUrl (server-relative root folder), webRelativeListUrl (no leading slash)" (`discover.js.j2:344-345`); the live CollabHome page the shape was copied from carries the same pair (`tests/test_refs.py:371-372`), and the copy path maps the two keys to *different* mapping fields, `url` vs `webRelativeUrl` (`refs.py:34-40`). `part_bind` instead copies one web-relative value into both keys (`dsl.py:263-264`) and refuses a leading slash outright (`dsl.py:257-262`), so the measured shape cannot be produced and the shape that *is* produced (`selectedListUrl: "Formwork Probe Docs"`) was never sent to a server. The commentary describing the measurement is wrong in three places: "the exact key set the M5 binding probe measured persisting … 6/6 blocks byte-exact" (`dsl.py:145-148, 218-221`) is true of the *keys* but silent on the *values*; "The measured values were container names ('Shared Documents')" (`dsl.py:255-256`) — no M5 sample contains `Shared Documents`, that string is from the CollabHome bundle; and `tests/test_dsl.py:856` pins `selectedListUrl == "Shared Documents"` while `:892-903` pins refusal of the server-relative form, so the suite currently enforces the defect. Fix: keep `listUrl` web-relative in the spec (that is the ergonomic input) and derive the server-relative value at compile time from the discovery document's web URL — `web.url` is `https://shauntestazure.sharepoint.com/sites/TestSampleTeam` in the fixture, and `urlparse(web.url).path + "/" + listUrl` reproduces both measured `serverRelativeUrl`s exactly (`/sites/TestSampleTeam/Formwork Probe Docs`, `/sites/TestSampleTeam/Lists/Formwork Probe Source`). That needs `Catalogue` to carry the web path (`parse_discovery` has `discovery["web"]` but drops it, `catalogue.py:285-317`). Then flip the two test pins to the measured pair and add a test that compiles a bind against `discovery.m5.json` and compares `properties` key-by-key with a persisted `webPartData.properties` from the fixture.
- **P2** The emitted binding is a strict subset of the shape that was measured, and the measured library entry is unreachable. Every measured ListWebPart binding also carries `webpartHeightKey: 4`, `hideCommandBar: false` and `serverProcessedContent.searchablePlainTexts.listTitle` (`discovery.m5.json:4239-4252`, `discover.js.j2:357-367`); `_control_for` emits `serverProcessedContent: {}` (`dsl.py:491`) and only the manifest entry's two defaults plus the four bind keys. Whether a List part renders without `listTitle`/`webpartHeightKey` is unmeasured, so "measured persisting" describes the probe's control, not the compiler's. Separately, the live catalogue's ListWebPart has **two** preconfigured entries — `List` (`isDocumentLibrary: false`) and `Document library` (`isDocumentLibrary: true`) — and `parse_discovery` takes only `entries[0]` for title and defaults (`catalogue.py:296-297, 302, 305`). So against a real discovery document `component: Document library` refuses as "not placeable" (`by_title` only sees entry 0), and `bind:` on `ListWebPart` always emits the *list* entry unless the author also writes `properties: {isDocumentLibrary: true}` and a `displayTitle`. The test suite does not notice because its synthetic catalogue has a `DocumentLibraryWebPart` alias (`tests/test_dsl.py:47-49`) that does not exist in `discovery.m5.json` (aliases there: `ListWebPart` ×2 entries, no `DocumentLibraryWebPart`). Suggest an `entry:` key (or resolving titles across all entries) as the M5 follow-up, and at least one `TestBind` case that compiles against the real fixture.
- **P2** GUID normalisation. `_GUID_RE` (`dsl.py:163-165`) accepts upper-case hex and braces, and because both braces are independently optional it also accepts the asymmetric `{guid` and `guid}`; the value is then written verbatim (`dsl.py:253`). Every measured id is bare lower-case (`discovery.m5.json:4605, 4755` and the `listBindings.fixtures` rows), so `{B90CA2AC-…}` reaches the stored bytes in a shape no probe sent. Fix: normalise to `value.strip("{}").lower()` after matching, or refuse non-canonical input; either way require the braces to be paired.
- **P3** `part_bind` never reads its `component` argument (`dsl.py:215-265`), so `bind:` is accepted on any component. Binding was measured on ListWebPart only (the two Quick links rows in the same block carry none of the `selected*` keys — `discovery.m5.json`, ids `…-0007-000000000003/06`, so the "6/6" in `dsl.py:147-148, 221` is 4/4 for the key set it names). `bind:` on `NewsWebPart` compiles; on `EventsWebPart`, whose defaults already carry `selectedListId: ""` (`discovery.m5.json:3807`), it adds three keys the part does not have. A refusal for components without a measured binding sample, citing `cat.list_bindings`, would keep the "measured, not guessed" line.
- **P3** `_control_for`'s new `cat` parameter is never used (`dsl.py:460-464`, body `:476-520`), and `if cat is not None` at `dsl.py:637` is dead because `compile_page` types `cat: Catalogue`. Both read like an intended catalogue-aware path that was not finished.
- **P3** The test's M5 shape does not resemble the wire shape. `M5_DISCOVERY` puts the containers under a top-level `probeLists` (`tests/test_dsl.py:671-684`) that `_probe_lists` never reads (it reads `listBindings.fixtures`, `catalogue.py:434-437`), and `_make_binding_sample` writes flat `listId`/`listUrl` with a string `target` (`:639-650`) where `_list_bindings` expects a `target` dict with `key`/`listId`/`serverRelativeUrl` (`catalogue.py:465-475`), so those rows parse into `ListBinding`s with empty target and id. Harmless today only because the DSL never reads `list_bindings`.

## Residual risk

The stated design is "measured, not guessed", and the two P1s are both places where the code cites the M5 fixture for a shape the fixture does not contain: the binding URL pair, and (by omission) the preview's geometry. Fixing the URL pair is mechanical once the catalogue carries the web path; until then a page compiled with `bind:` is the first formwork output whose list-binding bytes differ from every stored sample in the tree, and the apply script's byte-exact check will pass on it because SharePoint stores what it is sent — the failure, if any, would be a List part that renders empty or errors, which nothing in the pipeline can see. The P2s are one traceback path (dates), one KeyError path, one unasserted test and one unreachable manifest entry; all fail loudly or are visible in review. mypy was not run; the unused `cat` parameter and `if cat is not None` would not trip `strict`, but a run is still owed.
