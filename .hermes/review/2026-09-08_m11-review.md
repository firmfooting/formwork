## P1 — must fix before merge

### P1-1. The 3.12/3.13 matrix is inert: `matrix.python-version` is declared and never used

`ci.yml:15` adds `python-version: ["3.11", "3.12", "3.13"]`, but nothing
consumes it. The `test` job's only steps are `checkout` (`:20`),
`astral-sh/setup-uv` with **no `with:` block** (`:23`), `uv sync --frozen`
(`:25`) and `uv run --no-sync pytest -q` (`:27`). There is no `setup-python`,
no `python-version` input to setup-uv (which is what sets `UV_PYTHON`), and no
`--python` on `uv sync`. The three legs per OS are byte-identical
configurations; uv picks whatever interpreter it finds first, and picks the
same one all three times.

Concrete failure: the branch claims — in the CHANGELOG (`CHANGELOG.md:15`,
"CI tests against Python 3.11, 3.12 and 3.13") and in the plan item it closes —
coverage that does not exist. The suite is executed on **one** interpreter per
OS, and which one is not pinned or knowable from the workflow. The very class
of bug the branch fixed in fcb4472 (argparse's `%r` of an invalid choice gained
quotes in 3.12) is exactly what this matrix was added to catch, and it still
cannot catch the next one. Worse, the local `.venv` is 3.11.15
(`.venv/pyvenv.cfg:3`), so that argparse fix has never been executed on a 3.12+
interpreter anywhere — not locally, not in CI. It is asserted, not measured;
on a repo whose whole discipline is "measured, with evidence", that is the
finding.

Fix (one line):

```yaml
      - uses: astral-sh/setup-uv@c771a70e6277c0a99b617c7a806ffedaca235ff9 # v9.0.0
        with:
          python-version: ${{ matrix.python-version }}
```

and I would make it observable — add a `uv run --no-sync python -VV` step, so
the log proves which interpreter ran rather than leaving it to the job name.

### P1-2. The release job runs `gh` with no repository context, so no release is ever created

`release.yml:40-48`: the `release` job's steps are `download-artifact` and then
`gh release create "${GITHUB_REF_NAME}" dist/* --generate-notes`. There is no
`actions/checkout` in that job, and no `GH_REPO` in its env.

`gh` resolves the target repository in this order: the `-R/--repo` flag, then
the `GH_REPO` environment variable, then the git remotes of the current
working directory. None of the three is available here — the workspace contains
only the downloaded `dist/`, and `gh` does not read `GITHUB_REPOSITORY`.

Concrete failure: pushing `v0.7.0` builds and uploads the artifacts, then the
release step exits non-zero ("not a git repository" / "none of the git remotes
… point to a known GitHub host"). No GitHub release is created, no wheel is
attached — the entire M11 release path does nothing, and this is only
discoverable by cutting a real tag, since nothing in CI exercises `release.yml`.

Fix (one line, and harmless even if I am wrong about `gh`'s fallback order —
see the honesty note):

```yaml
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          GH_REPO: ${{ github.repository }}
```

### P1-3. README documents a PyPI install that nothing in the repo can produce

`README.md:504-516` tells the user to run `pipx install formwork` or
`pip install formwork`, under the heading "From a release wheel". Neither
command installs from a release wheel — both resolve the name `formwork` on
PyPI — and nothing in this repository ever publishes to PyPI: `release.yml`
only calls `gh release create`, there is no `twine`/`pypa/gh-action-pypi-publish`
step and no trusted-publisher config anywhere (grep for `pypi|twine|publish`
across the repo returns only prose and SharePoint's `publish` REST call).

Concrete failure: a reader of the front-page install section either gets
`ERROR: No matching distribution found for formwork`, or — if the name is
already taken on PyPI by an unrelated project — installs a stranger's package
and runs its `formwork` entry point. The first outcome is embarrassing; the
second is a code-execution footgun introduced by documentation.

Fix: document what the workflow actually produces, e.g. `pipx install
https://github.com/firmfooting/formwork/releases/download/v0.6.0/formwork-0.6.0-py3-none-any.whl`,
and keep the PyPI lines for when a publish step exists. If PyPI is intended
for M11, the publish job is the missing work, and the name should be claimed
before the README advertises it.

Secondary, same section: "Both give you the `formwork` command. The paste-in
generators print scripts that run in your browser" — `formwork gen findprobe`
requires `FINDINGS.md` in the working directory (`cli.py:150-156`), so from a
pipx install it fails with "no findings registry at FINDINGS.md: run from the
repository root". Worth one clause of honesty in the install section.

## P2 — should fix, can follow

### P2-1. Nothing verifies the wheel ships the templates; the CHANGELOG says it does

`CHANGELOG.md:19-21` states "The wheel is verified to ship the Jinja templates
(a wheel without them renders nothing) and is smoke-tested with a clean `pip
install`". That verification was a one-time manual act. No test, no CI job and
no release step re-checks it: `ci.yml` runs the suite from the source tree,
and `release.yml:28-29` builds and uploads without inspecting the result.

Concrete failure: `[tool.setuptools.package-data] formwork = ["templates/*.j2"]`
(`pyproject.toml:41-43`) is a **non-recursive** glob. The moment someone moves
the four shared partials into `src/formwork/templates/probes/` — a natural
tidy-up, given `_probe_setup.js.j2` and friends are already prefixed as
partials — the wheel silently ships without them, every gate stays green, and
the first symptom is `TemplateNotFound: _probe_setup.js.j2` in a user's
`formwork gen discover`. This is the core risk of a distribution milestone and
it is the one thing the milestone did not gate.

Fix: a `package` job — `python -m build`, then in a clean venv `pip install
dist/*.whl` and run `python -c "from formwork.generator import
generate_findprobe_script"` plus `formwork gen extract > /dev/null`; assert the
wheel's `RECORD` lists as many `.j2` files as `src/formwork/templates/`
contains. Or switch the glob to `templates/**/*.j2` and still gate it.

### P2-2. `test_a_version_bump_does_not_move_the_goldens` is a strict duplicate of the golden test — it does not test bump-independence

`test_generator.py:716-728`. Precisely: it is not *vacuous* (it does assert
golden equality), but it is **redundant** — it can only fail when
`test_script_matches_golden` also fails, and it never varies the version.

The reduction, step by step:

1. `version_normalised` (`:101-110`) always folds `__version__`, the *current*
   version. Nothing in this test substitutes a different one, so "fold with a
   DIFFERENT version" (docstring, `:719`) never happens.
2. `version_normalised(committed)` at `:728` is a **no-op**: the committed
   goldens contain no occurrence of `0.6.0` (verified by grep), because they
   are sentinel-bearing.
3. So the assertion reduces to `version_normalised(generate()) == committed` —
   character-for-character the assertion already made at `:707-709`.

The docstring's claim that it checks "EVERY version literal in the generated
output comes from the single `__version__` constant" is false: a template that
hard-coded `0.5.0` (a literal that already appears in `apply.js.j2`'s comparator
documentation) passes this test as happily as the real thing.

Concrete failure: the branch's headline guarantee is presented as *tested*, in
the commit and in `CHANGELOG.md:22-26`, when it rests entirely on the one-sided
fold in `test_script_matches_golden`. A future maintainer "simplifying" the
duplicate pair — or making the main test symmetric to match its own docstring
(see P3-2) — removes the real guard while this test keeps passing, and the next
bump quietly rewrites five goldens again.

Fix: make it a real bump. Monkeypatch the version where the generator actually
reads it (`generator.py:32` binds `__version__` at import, so
`monkeypatch.setattr(formwork.generator, "__version__", "9.9.9")`), regenerate,
fold by `"9.9.9"`, and compare against the committed goldens unchanged. That
test fails if any version literal is not sourced from the constant. Or delete
it and instead assert the invariant it wanted:
`GOLDEN_VERSION_SENTINEL in committed and __version__ not in committed`.

### P2-3. `version_normalised` folds the version *anywhere*, including embedded FINDINGS measurement text

`test_generator.py:110` is a bare `str.replace(__version__, SENTINEL)` over the
whole script. The findprobe golden embeds operator-written measurement prose
verbatim: `tests/fixtures/expected/findprobe.js:317-323` carries `"result":
"fresh 0.1 checked out; checkoutpage 200; publish 200 -> 1.0, checked out
false"` straight out of `FINDINGS.md:57`. And FINDINGS prose already names
formwork versions — `FINDINGS.md:56`: "the create-then-MERGE path apply used
before 0.5.0".

Concrete failure: the first FINDINGS row whose embedded `result` names the
*then-current* version (writing "apply since 0.7.0 sends PromotedState at
create" while the package is at 0.7.0 is an entirely natural thing to do) has
that datum rewritten to `__FORMWORK_VERSION__` in the committed golden. The
golden then records a measurement that was never measured; and at the next bump
the generated side emits the real `0.7.0` again — which no longer folds — so
the golden fails for a reason that has nothing to do with any change, and the
"fix" (regenerate) rewrites the data back. The fold is exactly as wide as the
version string and no wider.

Fix: fold the version only in the positions that carry it —
`re.sub(rf'(v|FORMWORK_VERSION = "|formworkVersion: "){re.escape(__version__)}',
...)` or, minimally, fold the delimited forms `f"v{__version__}"` and
`f'"{__version__}"'` rather than the bare substring.

### P2-4. Node coverage went **down**, silently, in a commit whose plan item asked to increase it

020de82 deleted `TestExtractScript.test_script_is_syntactically_valid_javascript`
(confirmed with `git log -S`), the only local `node --check` of the extract
script. Nothing mentions it: not the commit message, not `CHANGELOG.md:15-27`.
The sibling tests survive (`test_generator.py:155` for discover, `:478` for
apply), so this is an inconsistency, not a policy change.

Meanwhile the M11 plan (`.hermes/plans/2026-09-07_milestone-ledger-m6-m10.md:100`)
says "add the discover script to the CI node gate". `ci.yml:62,65` still imports
and checks only `generate_extract_script` and `generate_apply_script`. The
discover and findprobe scripts — the two largest generated files — are
syntax-checked *only* by local tests, on machines that happen to have node.

Concrete failure: a template edit that breaks `discover.js.j2`'s JavaScript
syntax passes CI. The goldens compare text, not syntax, so a mismatched brace
in a partial produces a golden diff a regenerating maintainer accepts, and CI
is green.

Fix: restore the deleted extract test, and add `generate_discover_script()` and
`generate_findprobe_script(load_findings(...))` to the node-gate list at
`ci.yml:65-66`.

### P2-5. `uv sync --frozen` has no drift gate, and the README still tells contributors to use pip

`ci.yml:25,39,58` all use `uv sync --frozen`. `--frozen` means "use the
lockfile as-is, do not check it" — it is `--locked` (or `uv lock --check`) that
asserts the lock still matches `pyproject.toml`. The comment at
`pyproject.toml:19-21` ("uv.lock is the single source of truth for what the
gates run against — a PR cannot pass CI on locally-upgraded deps") is true of
what CI *installs*, but it implies a consistency guarantee that `--frozen` does
not provide.

This compounds with `README.md:524`, which still tells contributors to develop
with `python -m venv .venv && .venv/bin/pip install -e '.[dev]'`. Nobody
following the README ever runs `uv lock`, so nobody notices the lock going
stale.

Concrete failure: a PR raises `jinja2>=3.1` to `jinja2>=3.2` in
`pyproject.toml` (or adds a dependency) and does not relock. CI resolves
nothing, installs the locked jinja2 3.1.6, and goes green — so the floor the
published wheel declares is never the floor that was tested, and a new
dependency's absence is caught only if some import happens to fail.

Fix: `uv sync --locked` in all three jobs (or one `uv lock --check` step), and
one line in the README's Development block giving the uv path
(`uv sync && uv run pytest`) so contributors relock.

### P2-6. The release path has no test gate, no tag↔version check, and an unpinned build toolchain

`release.yml:8-10` fires on any `v*` tag; `jobs.build` (`:15-33`) does
`pip install build` then `python -m build`. Three gaps, one workflow:

- **No test gate.** Nothing in `release.yml` runs pytest, ruff or mypy, and
  nothing requires the CI run for that commit to have passed. A tag on a broken
  `main` — or on any commit at all, including one that never saw a PR — builds
  and publishes.
- **No tag/version consistency check.** `pyproject.toml:7` is the version the
  artifacts are named after; `GITHUB_REF_NAME` is what the release is named
  after. Nothing ties them. This branch *institutionalises* the gap: the
  CHANGELOG's new Unreleased convention (`CHANGELOG.md:10-13`, "no version bump
  yet") means the version literal now routinely lags merged work, so tagging
  `v0.7.0` before bumping produces a release page titled v0.7.0 carrying
  `formwork-0.6.0-py3-none-any.whl`. Whoever downloads it gets 0.6.0 and no
  warning.
- **Unpinned build toolchain in the one job whose output is published.**
  `pip install build` (`:27`) resolves `build`, and `python -m build` then
  resolves `setuptools>=68` from `pyproject.toml:2` — both at run time, both
  unpinned and unhashed, in the path that produces the artifact users execute.
  That is the weakest link in a branch whose stated house rule is SHA-pinning
  every action. `.github/workflows/zizmor.yml:25` has the same shape:
  `uvx zizmor` installs whatever version PyPI serves that day, and runs it with
  `GH_TOKEN` in the environment — so the security gate is both non-reproducible
  (a new zizmor release can red the build with no repo change) and itself
  unpinned.

Fix: gate the build job on the suite (run `uv sync --locked && uv run pytest -q`
before `python -m build`, or make `release` depend on a reusable call of CI);
add three lines asserting `GITHUB_REF_NAME == "v" + version` from
`pyproject.toml` and failing loudly otherwise; pin `pip install
build==<version>` and `uvx zizmor@<version>`.

## P3 — nits

### P3-1. Stale docs that still believe the goldens carry a real version

Four places, all now false, all read by whoever next touches the goldens:

- `tests/test_generator.py:5-8` (module docstring, the one both golden tests
  point at for the regeneration command): "hold the emitted scripts byte for

- `tests/test_version.py:3-7`: "formwork.`__version__` is what the paste-in

- `src/formwork/generator.py:26-27`: "The emitted bytes are pinned by the
  goldens under `tests/fixtures/expected`."
- `README.md:539-543` describes the golden contract without the version
  caveat, right where it tells a maintainer to regenerate and review the diff.

### P3-2. `test_script_matches_golden`'s docstring contradicts its own code

`test_generator.py:700-701` says "the formwork version, which **both sides**
fold to the sentinel before comparison"; the code four lines later
(`:706-708`) folds only the generated side, with a comment saying exactly that.
`CHANGELOG.md:22-23` repeats the wrong version ("folds the version string on
both sides"). The one-sided fold is not an implementation detail — it is what
makes a version-carrying golden fail loudly. A maintainer who trusts the
docstring and "fixes" the asymmetry destroys the invariant, and P2-2's
duplicate test would not notice.

### P3-3. `TestExtractScript` is still gated on node, but no longer uses it

`test_generator.py:127` keeps `@pytest.mark.skipif(not node_available())` on a
class whose three remaining tests (`:130-150`) are pure string assertions — the
only node user in it was the test P2-4 deleted. On any machine without node,
three real assertions about the extract script now skip for no reason.

### P3-4. Two M11 plan items were dropped without a word

`.hermes/plans/2026-09-07_milestone-ledger-m6-m10.md:99-102` lists four items.
The discover node-gate (P2-4) and "`.gitattributes` eol pin lands here" were
not done — there is no `.gitattributes` in the tree. The eol pin was
specifically about the Windows legs this branch just tripled; without it the
goldens are protected only by `write_golden`'s explicit `newline="\n"`
(`test_generator.py:81-84`) and by `read_text`'s universal-newline translation
on the read side. That happens to be enough today, which is why this is a P3
and not higher — but the plan item was closed silently, and the CHANGELOG
entry reads as if M11 were complete.

### P3-5. The Unreleased guard is loose in one direction

`tests/test_version.py:31-33` strips a leading Unreleased heading. Two
consecutive `## Unreleased` sections *are* caught (the second one fails the
`startswith` on line 34, with a confusing message). An Unreleased section
placed *after* the version heading passes silently — `headings[0]` is the
version, the guard is satisfied, and the unreleased work sits buried below a
release. Acceptable as-is, in my view; if you want it strict, assert that
`"## Unreleased"` occurs at most once and, when present, is the first heading.

### P3-6. Two small false statements and one operational snag

- `CHANGELOG.md:24` offers as evidence that "`.venv/bin/python
  tests/test_generator.py` output is empty across a bump". That script prints
  `wrote {path}` for every golden (`test_generator.py:741`), so its output is
  never empty. The intended claim — the resulting `git diff` is empty — is the
  one worth stating, since it is the actual proof.
- `pyproject.toml:15-19` now declares the dev set twice, as
  `[project.optional-dependencies].dev` and `[dependency-groups].dev`, with
  nothing asserting the two lists agree. They will drift.
- Adding `python-version` to the matrix renames every test job (`test
  (ubuntu-latest)` → `test (ubuntu-latest, 3.11)`). Any branch-protection
  required-status-check on the old names must be updated or `main` blocks on
  checks that no longer exist.

## Honesty note — what I could not verify

I had no execution in this session: no pytest, no uv, no `python -m build`, no
`gh`, no zizmor, and no network (both web fetches were denied). Everything
above is read from the sources in the worktree plus read-only git. Specifically:

- **P1-2 (`gh` without repo context)** is reasoned from gh's documented
  resolution order (`-R` → `GH_REPO` → git remotes) and from the absence of a
  checkout in that job. I could not open the gh manual to re-confirm that gh
  ignores `GITHUB_REPOSITORY`, and I have not run the workflow. I am confident
  but not certain; I rated it P1 anyway because the fix is one line and is
  harmless if I am wrong, and because the failure is otherwise only discovered
  by cutting a real tag.
- **P1-3**: I could not reach PyPI, so I do not know whether the name
  `formwork` is unclaimed (install fails) or claimed by someone else (install
  succeeds with a stranger's code). What I *did* verify is that nothing in this
  repository publishes to PyPI, which is what makes the README wrong either way.
- **P1-1**: I verified `matrix.python-version` is unreferenced anywhere in
  `ci.yml`, which is sufficient for the finding. Which interpreter uv actually
  selects on the runners is a guess (the runner's system python, or a downloaded
  managed one) — I did not verify it and the workflow does not log it.
- **Claim 1's bump experiment** (0.6.0 → 9.9.9, regenerate, compare hashes):
  not reproducible here — the worktree is clean at 0.6.0 and I could not run
  the regenerator. I did not take the claim on trust; instead I argued the
  property from the sources (`{{ version }}` is the only path from
  `__version__` into the templates, and no golden contains the current version
  literal), and it holds. The property is real; the *test* that claims to prove
  it is not (P2-2).
- **Packaging**: the wheel I inspected is the untracked `dist/` artifact built
  in this worktree at 0.6.0, read by grepping the zip's stored filenames — all
  nine templates confirmed. I could not read the sdist (gzipped, and I could
  not run `tar`). Modern setuptools does include `package_data` in sdists via
  `build_py.data_files`, so I expect the sdist is fine, but I am reasoning, not
  measuring — that is part of why P2-1 asks for a gate rather than a re-check.
- **zizmor's "zero findings"**: not run. I walked the audits I know
  (`artipacked`, `excessive-permissions`, `unpinned-uses`, `template-injection`,
  `cache-poisoning`) against all three workflows by hand and found nothing that
  should fire, which is consistent with the claim. Whether the *floating*
  zizmor version keeps returning zero is exactly the reproducibility problem in
  P2-6.
- **Windows**: no Windows leg was executed. I found nothing Windows-fragile in
  the new files (the node-gate heredoc and its `/tmp` paths are ubuntu-only),
  and the CRLF hazard is handled by `write_golden`'s explicit newline plus
  universal-newline reads — but the missing `.gitattributes` (P3-4) means that
  protection is convention, not enforcement.
